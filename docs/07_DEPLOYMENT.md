# Деплой Спортика через GitHub Actions и SSH

Конфигурация подготовлена для дальнейшего использования. Добавление этих файлов
не выполняет реальный деплой. Не включайте `DEPLOY_ENABLED`, пока сервер не готов.

## Компоненты

`docker-compose.production.yml` запускает PostgreSQL 18.1, миграции migrate 4.19.1,
Go backend, генератор планов `ai/main.py`, ML-чат и frontend на nginx.
База и внутренние API не публикуют порты на хосте. Frontend по умолчанию доступен
на `127.0.0.1:3000`; внешний reverse proxy завершает TLS и проксирует туда запросы.
Frontend обращается к `/api/v1` на том же домене; nginx также обслуживает `/static/`
и проксирует поток чата без буферизации. Данные PostgreSQL хранятся в именованном
томе `sportik_postgres_data`, независимо от каталога релиза.

Go-образ запускается от непривилегированного пользователя, содержит изображения
упражнений, CA-сертификаты и часовые пояса. Версия Go берётся скриптом деплоя из
`backend/go.mod` и передаётся при сборке. Frontend собирается через `npm ci`.
Python-образ использует существующий `ai/Dockerfile` и зависимости ML API;
модель CatBoost и датасет включаются из репозитория. Файлы `.env`, локальные
артефакты сборки и зависимости исключены из Docker-контекстов.

## Требования к серверу

- Linux с Docker Engine и Compose plugin **2.30+** (нужны `--wait` и необязательный `env_file`).
- `sh`, `tar`, `awk`, `flock` из util-linux, OpenSSH Server; доступ к Docker Hub,
  Go proxy, npm и PyPI для сборки. Для Cerebras нужен исходящий HTTPS.
- Начальный ориентир ресурсов для сборки всего стека: 2 CPU, 4 ГБ RAM и 20 ГБ
  свободного диска; реальные потребности проверяются на целевом сервере.
- Отдельный SSH-пользователь с ключом, доступом к Docker и правом записи
  в `/srv/sportik`. Доступ к Docker даёт полномочия управления хостом.
- Межсетевой экран разрешает SSH на выбранном порту и HTTPS reverse proxy.
  PostgreSQL и ML-порты наружу не открываются.
- Резервное копирование БД и проверенный порядок восстановления до первого релиза.

## GitHub Secrets и Variables

Создайте GitHub Environment `production`. Для включённого CD рекомендуется
ограничить его веткой `main`; при необходимости настройте обязательное одобрение.

| Secret | Значение |
|---|---|
| `HOST` | IP или домен сервера без схемы URL |
| `USER` | SSH-пользователь деплоя |
| `SSH_KEY` | Приватный SSH-ключ; публичный установлен в `authorized_keys` |
| `SSH_PORT` | Явный SSH-порт, число 1–65535 |
| `SSH_KNOWN_HOSTS` | Проверенная строка known_hosts сервера; для нестандартного порта адрес имеет вид `[host]:port` |
| `TELEGRAM_TO` | ID чата, куда бот может отправлять уведомления |
| `TELEGRAM_TOKEN` | Токен Telegram-бота |

Единственная GitHub Variable — `DEPLOY_ENABLED=true`, без неё job деплоя
пропускается. Пока готовится конфигурация, оставьте переменную отсутствующей
или равной `false`. Secrets можно задать на уровне Environment или репозитория.
CI их не использует. Telegram получает итог `success`/`failure` и ссылку на запуск.

Получите SSH host key по доверенному каналу: сравните отпечаток на серверной
консоли (`ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`) с полученной строкой
known_hosts. Не сохраняйте результат непроверенного `ssh-keyscan` как доверенный.
Workflow использует `StrictHostKeyChecking=yes` и временный файл ключа с правами 600.

## Переменные окружения приложения

На сервере создайте `/srv/sportik/shared/.env.production`, взяв за основу
`deploy/.env.production.example`. Этот файл не входит в релизы и не отправляется
через GitHub. Пример содержит только заглушки для проверки Compose.

| Переменная | Назначение / значение по умолчанию |
|---|---|
| `POSTGRES_DB`, `POSTGRES_USER` | Имя БД и пользователя; пример `sportapp` |
| `POSTGRES_PASSWORD` | Обязательный случайный пароль; используйте URL-safe hex, поскольку migrate получает URI |
| `JWT_SECRET` | Обязательный случайный секрет подписи JWT |
| `JWT_TOKEN_TTL` | Срок действия JWT: `2160h` |
| `POSTGRES_TIMEOUT` | Таймаут операций БД: `5s` |
| `ML_TIMEOUT` | Таймаут HTTP генератора: `30s` |
| `ML_CHAT_TIMEOUT` | Отдельный HTTP-таймаут чата: в production-примере `60s`; без настройки backend сохраняет общий `ML_TIMEOUT` |
| `ML_GENERATION_TIMEOUT` | Общая граница генерации плана: `52s` |
| `ML_SERVICE_TOKEN` | Обязательный отдельный случайный токен Go ↔ ML v2; Compose передаёт одинаковое значение обоим сервисам. Deadline генерации v2 — 8 секунд |
| `HTTP_SHUTDOWN_TIMEOUT` | Ожидание завершения HTTP-запросов: `30s` |
| `LOGGER_LEVEL` | Уровень журнала: `INFO` |
| `HTTP_BIND`, `HTTP_PORT` | Адрес и порт frontend на хосте: `127.0.0.1`, `3000` |
| `ML_ENV_FILE` | Путь к секретам ML-чата: `/srv/sportik/shared/ml.env` |

`HTTP_ADDR=:5050`, `LOGGER_FOLDER=/app/logs`, адрес БД `postgres:5432` и URL
`http://ml:8000`, `http://ml-chat:8000` задаёт Compose для внутренней сети.
`RELEASE_ID` и `GO_VERSION` скрипт вычисляет для каждого релиза; не меняйте их вручную.
`VITE_API_URL` оставлен пустым: пути `/api/v1/...` уже заданы в frontend,
поэтому дополнительный префикс дублировал бы их. `VITE_USE_WORKOUT_MOCKS=false`
задаётся при сборке frontend.

В `shared/ml.env` при необходимости сохраните `CEREBRAS_API_KEY=...`.
Без файла/ключа ML-чат использует существующий резервный режим. Health check
не отправляет пользовательские сообщения и не вызывает платные AI API.
Пароль БД и JWT создаются отдельно, например `openssl rand -hex 32`.
Не публикуйте их в git, отчёте, выводе CI или полной распечатке `docker compose config`.

## Первоначальная настройка

1. Установите перечисленные инструменты и настройте SSH. Публичный ключ деплоя
   добавьте в `~/.ssh/authorized_keys` пользователя сервера.
2. Создайте каталоги и передайте их пользователю деплоя (замените `deploy`):

   ```bash
   sudo mkdir -p /srv/sportik/shared /srv/sportik/incoming /srv/sportik/releases
   sudo chown -R deploy:deploy /srv/sportik
   chmod 700 /srv/sportik/shared
   ```

3. Сохраните заполненный `.env.production` и необязательный `ml.env` в `shared/`,
   установите права `chmod 600` на эти файлы. При переносе существующей БД сначала
   сделайте резервную копию; не подключайте новый том вместо старых данных без миграции.
4. Подготовьте TLS reverse proxy на `127.0.0.1:3000`, резервные копии и ротацию Docker-логов.
   Файловые логи backend в контейнере считаются временными; постоянное хранилище
   журналов настраивается отдельно на сервере.
5. Задайте Secrets, проверьте host key, затем включите `DEPLOY_ENABLED=true`.
   На этапе подготовки этой задачи этот шаг **не выполняется**.

## Автоматический и ручной запуск

Автоматический путь: push в `main` → успешный `Backend CI` → `Deploy production`.
Проверяются тип события `push`, ветка и исходный репозиторий; успешный CI для PR
не вызывает деплой. `workflow_run` начинает работать после попадания workflow в
основную ветку. Автодеплой использует SHA успешного CI, а не произвольный свежий HEAD.

Ручной путь: Actions → Deploy production → Run workflow → ветка `main`.
Запуск с другой ветки пропускается. Перед SSH повторяются установка линтера,
`make check build`, тесты скрипта и проверка Compose; это также защищает ручной запуск.

Workflow архивирует проверенный commit через `git archive` и передаёт архив и
`scripts/deploy.sh` по SSH/SCP. Серверу не нужен доступ к приватным GitHub-ключам.
Скрипт последовательно:

1. Проверяет окружение и полный SHA, берёт серверную блокировку `flock`.
2. Распаковывает исходники в `/srv/sportik/releases/<SHA>` и собирает образы с тегом SHA.
3. Ожидает готовности PostgreSQL, выполняет `migrate up` до замены приложения.
4. Запускает стек с `--no-build --wait` и проверяет HTTP `/healthz` и `/` через frontend.
5. Только после успеха переводит `/srv/sportik/current` на новый релиз,
   сохраняя путь прежнего в `/srv/sportik/previous-release`.

Готовность Go API включает `SELECT 1` с таймаутом; отказ БД возвращает 503 без
раскрытия ошибки. Compose отдельно проверяет оба ML-процесса. Health check
генератора выполняется после загрузки модели и датасета.

GitHub concurrency и серверный `flock` не допускают одновременной замены сервисов.
Это обычный Compose-деплой с возможным кратким перерывом; нулевой простой не обещается.
Каталоги релизов, архивы и образы автоматически не удаляются, чтобы сохранить откат.

## Откат и ошибки

Если health check нового приложения не прошёл, скрипт пытается запустить предыдущие
образы и проверить их, оставляя job неуспешным. При первой установке без прошлого
релиза требуется исправить причину и повторить деплой. При ошибке миграций замена
приложения не начинается; автоматического `migrate down` нет.

Для ручного отката на сервере укажите полный SHA сохранённого релиза:

```bash
sh /srv/sportik/current/scripts/deploy.sh rollback <полный_SHA_релиза>
```

Можно взять предыдущий SHA из имени каталога, записанного в
`/srv/sportik/previous-release`. Откат не пересобирает образы, не выполняет миграции
и не удаляет том БД. Сохраняйте соответствующие каталоги и образы.

Миграции релиза должны быть обратно совместимы с предыдущим кодом. Для разрушительных
изменений схемы нужен отдельный план и проверенная резервная копия: откат приложения
не восстанавливает БД. До первого реального обновления проверьте `pg_dump` и восстановление
на отдельной БД. Не запускайте `docker compose down -v` на production.

## Проверка без сервера

```bash
make -C backend lint-install check test-cover build
python3 -m unittest discover -s scripts/tests -v
sh -n scripts/deploy.sh scripts/install-golangci-lint.sh
docker compose --env-file deploy/.env.production.example -f docker-compose.production.yml config --quiet
```

Локальная сборка контейнеров (сама по себе не запускает приложение):

```bash
docker compose --env-file deploy/.env.production.example -f docker-compose.production.yml build backend ml frontend
```

Тесты скрипта подменяют Docker и блокировку, проверяя успешный запуск, отказ миграций,
отказ готовности, восстановление предыдущего релиза, ручной откат и неверные входные
данные. Проверку настоящего SSH, Telegram и целевого сервера выполняют при вводе CD
в эксплуатацию после настройки секретов.

Формат golangci-lint сверяется с [официальной документацией](https://golangci-lint.run/docs/configuration/file/),
ограничения события `workflow_run` — с [документацией GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run).
