# Безопасная SQL-миграция

1. Прочитать корневой и `backend/AGENTS.md`, `docs/04_DATABASE.md`, последние файлы `backend/migrations/` и SQL репозитория. Определить изменения схемы, владельцев данных, ограничения, блокировки и совместимость текущего приложения.
2. Добавить следующую свободную последовательную пару `<номер>_<имя>.up.sql` / `.down.sql` (6 цифр), не переписывать уже применённые миграции. Источник схемы — SQL в `backend/migrations/`; здесь нет ORM-миграций. При необходимости `make -C backend migrate-create seq=<имя>` создаёт пару через Docker, но не применяет её.
3. Предпочитать совместимое добавление полей/индексов; описать backfill, default/NULL, уникальность и влияние на существующие записи. Проверить `user_id`, внешние ключи, `version` и `deleted_at` там, где они используются. Откат с потерей данных явно отметить: не обещать восстановление удалённых значений.
4. Подготовить отдельную одноразовую PostgreSQL и синтетические фикстуры, включая две записи разных владельцев, пустые таблицы и граничные значения затронутых полей. До исполнения убедиться в тестовом имени/адресе БД; не наследовать реквизиты рабочей `.env`. Не печатать DSN/пароли в логи.
5. На этой БД применить базовые миграции → фикстуры → новую up → проверки схемы/данных и SQL репозитория → down новой миграции → повторную up. Проверить откат именно новой миграции. **Не запускать** `env-cleanup`, очистку рабочей БД и `make migrate-down`: существующая цель без числа откатывает все миграции и использует рабочую `.env`. Для одноразовой БД допустим отдельно настроенный migrate с `down 1`.
6. Выполнить целевые Go-тесты и `make -C backend verify`. Передать SQL, контракт и результаты отдельному субагенту на ревью. Указать проверенную версию PostgreSQL, фикстуры, результаты up/down/up и ограничения. Если тестовая БД недоступна, сохранить SQL и явно сообщить, что интеграционная проверка не выполнена.

## Пример из проекта

Пара `backend/migrations/000004_nutrition_grams.{up,down}.sql` добавляет размер порции:

```sql
-- up: существующие записи получают 100, NULL не разрешён
ALTER TABLE sportapp.nutrition_entries
    ADD COLUMN IF NOT EXISTS grams DOUBLE PRECISION NOT NULL DEFAULT 100;

-- down: удаляет поле и все сохранённые размеры порций
ALTER TABLE sportapp.nutrition_entries
    DROP COLUMN IF EXISTS grams;
```

Это фрагмент, а не новая миграция: полная пара меняет также `nutrition_dishes.base_grams` и исправляет неположительные значения. На тестовой БД проверить сохранение старых записей, default 100, вставку явных граммов и оба поля после повторного up; down уничтожает значения порций. Образ текущего локального Compose — PostgreSQL 18.1. Сам `verify` миграции не применяет и БД не запускает.
