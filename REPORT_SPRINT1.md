## 2. Результаты предварительного аудита кодовой базы

В ходе аудита текущих обработчиков, сервисов, репозиториев, middleware и конфигурации выявлены следующие проблемы (отсортированы по приоритету):

1. **[Критический] Нарушение слоистой архитектуры в модуле Nutrition:**
   - Монолитный файл `internal/features/nutrition/nutrition.go` (1425 строк) сочетал сырые SQL-запросы в HTTP-хендлерах, бизнес-формулы (Миффлин — Сан Жеор, расчёт макросов, целей по воде) и сериализацию ответов.
2. **[Критический] Баг с повторным вызовом `WriteHeader` в `core_http_responce`:**
   - В методе `errorResponse` выполнялся вызов `h.rw.WriteHeader(statusCode)`, после чего вызывался `h.JSONResponse`, также вызывавший `WriteHeader`. Это приводило к рантайм-предупреждению `http: superfluous response.WriteHeader call`.
3. **[Высокий] Обходы прав доступа и логика удаления объектов (IDOR):**
   - Метод `DeleteNotesUser` не проверял количество затронутых строк (`RowsAffected`). При попытке удалить чужую или уже удалённую заметку возвращался статус `204 No Content` вместо `404 Not Found`.
4. **[Высокий] Несогласованность регистрации пользователя в `/api/v1/auth/register`:**
   - Обработчик требовал обязательный заголовок `Authorization: Bearer <guest_token>`. Прямая регистрация без гостевой сессии возвращала `401 Unauthorized`, что ломало прямую регистрацию новых пользователей.
5. **[Высокий] Отсутствие таймаутов на внешние вызовы (ML-сервис):**
   - В `internal/features/mlclient` и `aichat.Service` отсутствовал настраиваемый таймаут HTTP-клиента, что грозило зависанием горутин при сетевых сбоях ML-модели.
6. **[Средний] Отсутствие пагинации и стабильной сортировки в списочных API:**
   - Методы заметок (`/api/v1/notes`), записей питания (`/api/v1/nutrition/entries`) и блюд возвращали несегментированные списки без параметров `limit`/`offset` и вторичной сортировки по `id`.
7. **[Средний] Потенциальная утечка памяти в in-memory rate limiter:**
   - В `slidingWindowLimiter` отсутствовала очистка устаревших записей из `map`, что вело к неограниченному росту памяти.
8. **[Средний] Отсутствие Go-тестов:**
   - В репозитории отсутствовали unit- и integration-тесты для критических бизнес-процессов.
9. **[Низкий] Отсутствие GoDoc-документации:**
   - Экспортируемые функции и структуры не содержали стандартных комментариев GoDoc.

## 5. Суть выполненных улучшений

### 5.1. Архитектурная декомпозиция питания (`nutrition`)
- Монолит `nutrition.go` полностью расформирован на независимые слои:
  - `repository/postgres/`: модели (`models.go`), общие SQL-запросы (`repository.go`), записи приёмов пищи (`entries.go`), избранное (`favorites.go`), цели и нормы веса (`goals.go`), каталог блюд (`dishes.go`), трекер воды и веса (`tracker.go`).
  - `service/`: изолированная бизнес-логика (`service.go`) — расчёт норм калорийности и БЖУ по формуле Миффлина — Сан Жеора, масштабирование нутриентов на 100 г, вычисление целевого объёма воды по массе тела, расчёт streak-серий, агрегация дашборда и аналитики.
  - `transport/http/`: обработчики запросов (`transport.go`), валидация входных данных, извлечение контекста пользователя, маппинг статус-кодов.
  - Корневой `nutrition.go` оставлен как компактный фасад, предоставляющий метод `RegisterRoutes` и сохраняющий существующий способ подключения в `main.go`.

### 5.2. Безопасность, авторизация и исправление дефектов ядра
- **Устранение двойного `WriteHeader`**: удалён преждевременный вызов статус-кода в `errorResponse`; обеспечена надёжная установка заголовка `Content-Type: application/json`.
- **Защита от паники в логгере**: метод `core_logger.FromContext` безопасно возвращает `Nop()`-логгер при отсутствии контекста вместо паники nil-pointer.
- **Устранение IDOR и защита удаления**: `DeleteNotesUser` теперь проверяет `RowsAffected() == 0`, возвращая `ErrNotFound` (404), если заметка не принадлежит пользователю или уже удалена.
- **Гибкая регистрация пользователей**: `/api/v1/auth/register` теперь корректно отрабатывает как сценарий прямой регистрации без гостевого токена (создавая новую учётную запись), так и промоут гостя с привязкой ранее собранных тренировочных данных.
- **Защита от зависаний внешних сервисов**: в `mlclient.Config` добавлен таймаут (по умолчанию 30s для генерации плана и 60s для AI-чата).
- **Очистка памяти лимитера**: `slidingWindowLimiter` получил периодическую очистку записей старше длительности окна, предотвращая утечки памяти.
- **Маскирование чувствительных данных**: middleware логгера автоматически маскирует параметры запросов `token`, `password`, `secret`, `key`, `auth` строкой `[REDACTED]`.

### 5.3. Пагинация и стабильная сортировка
- Для списочных методов реализованы параметры `limit` и `offset`.
- В ответ включается `total` (общее количество записей без учёта пагинации).
- Добавлена вторичная детерминированная сортировка по `id DESC` (например, `ORDER BY created_at DESC, id DESC`), устраняющая проблему прыгающих записей в PostgreSQL при одинаковых отметках времени.
- Схема API `/api/v1/notes` и спецификация OpenAPI (`openapi.json`, `openapi.yml`, `current.json`, `semester.json`) обновлены; коллекция Postman перегенерирована скриптом сборки.

### 5.4. Документирование кода (GoDoc)
- Добавлены структурированные GoDoc-комментарии ко всем ключевым модулям:
  - `internal/core/auth`: назначение, жизненный цикл токенов, генерация и парсинг клеймов.
  - `internal/core/errors`: соответствие доменных ошибок HTTP-статусам.
  - `internal/core/logger`: методы контекстной привязки, уровни логирования, освобождение ресурсов.
  - `internal/core/repository/postgres/pool`: интерфейсы пула соединений.
  - `internal/core/transport/http/middleware`: механизмы защиты, извлечение пользователя, CORS, panic recovery, rate limiting.
  - `internal/core/transport/http/responce`: маппинг ошибок, JSON-сериализация.
  - `internal/features/users/service`: регистрация, логин, оптимистичные блокировки (`UpdateProfile`), завершение тренировки (`CompleteWorkout`), заметки (`notes`).
  - `internal/features/nutrition/service`: расчётные формулы, бизнес-правила трекинга.
  - `internal/features/mlclient`: интеграция с ML-микросервисом, формат пейлоадов и обработка сбоев.

### 5.5. Комплексное тестирование
Создан набор unit-тестов, работающих полностью изолированно без необходимости поднятия внешней БД:
1. **Авторизация и JWT (`jwt_test.go`)**: создание токенов для зарегистрированных и гостевых пользователей, отклонение просроченных токенов, невалидных подписей и повреждённых строк.
2. **Middleware защиты (`auth_test.go`)**: проверка отсутствия/невалидности заголовка `Authorization`, извлечение клеймов в контекст запроса.
3. **Ограничение частоты (`rate_limit_test.go`)**: пороги запросов, скользящее окно, очистка памяти.
4. **Сервис пользователей (`users_service_test.go`)**: прямая регистрация, конвертация гостя, сравнение bcrypt-хешей при логине, оптимистичные блокировки версий (проверка 409 Conflict).
5. **Тренировочный процесс (`workout_test.go`)**: прогрессия весов (порог 12 повторений -> рост, <6 -> сброс), расчёт личных рекордов в хайлайтах сессии, разблокировка достижений.
6. **Заметки, пагинация и IDOR (`notes_test.go`)**: проверка параметров limit/offset/total, запрет изменения/удаления чужих записей (возврат 404).
7. **Клиент машинного обучения (`mlclient_test.go`)**: успешное маппирование упражнений, таймауты сетевых запросов, обработка статусов 500/502/503, обработка битого JSON.
8. **HTTP-слой питания (`transport_test.go`)**: список приёмов пищи с пагинацией, создание записей, пресечение попыток удаления чужих записей и блюд (IDOR).
9. **Бизнес-логика питания (`service_test.go`)**: калорийность макронутриентов, масштабирование порций, нормы воды, временные границы суток.
10. **HTTP-слой пользователей (`users_transport_http/transport_test.go`)**: гостевой доступ, прямая регистрация и промоут гостя, логин, пагинация заметок, валидация ID заметок (возврат 400 при нечисловом ID), защита от IDOR при удалении, optimistic locking профиля (409 при конфликте версий).

### 5.6. Автоматизация и CI/CD
- **Makefile**: расширен командами `test` (`go test -v ./...`), `test-cover` (профиль покрытия), `fmt` (`gofmt -s -w .`), `fmt-check`, `vet`, `lint`, `check`, `build`.

## 7. Ограничения и оставшиеся риски

1. **Внешняя интеграция с ML-сервисом**:
   - При недоступности стороннего ML-сервиса генерация плана возвращает ошибку; в перспективе целесообразно добавить локальный fallback-план на случай полного падения внешнего хоста.
2. **In-Memory Rate Limiting при горизонтальном масштабировании**:
   - Текущий лимитер использует память локального процесса. При запуске нескольких реплик бэкенда за балансировщиком рекомендуется перейти на распределённый Redis/Valkey rate limiter.
3. **Транзакционность сложных агрегатов**:
   - Метод `CompleteWorkout` выполняет сохранение истории, весов и достижений последовательными шагами; в следующем спринте рекомендуется обернуть всю цепочку в явную транзакцию `pgx.Tx` с rollback при ошибке на любом шаге.

### 8.3. Сохранение поведения и ограничения

- Значения формул, порогов и сроков не менялись. `0`, `1`, индексы SQL-параметров,
  размеры служебных буферов/срезов без предметного смысла и значения таблицы
  начальных весов упражнений не заменялись бессмысленными константами.
- Операции API v1 сохранены. Добавлен инфраструктурный `GET /healthz` с `SELECT 1`
  и ограничением времени; ошибки подключения не попадают в HTTP-ответ.
- Frontend собирается с пустым `VITE_API_URL`: действующие запросы уже содержат
  `/api/v1`, поэтому дублирование этого префикса недопустимо. nginx также
  проксирует изображения упражнений и потоковый чат.
- Автодеплой выключен, пока явно не включён `DEPLOY_ENABLED=true`. Секреты
  приложения хранятся на сервере вне релизов; CD передаёт только исходники.
- Откат приложения не откатывает схему БД. Нужны обратно совместимые миграции
  и проверенная резервная копия. Compose-деплой может иметь короткий перерыв;
  автоматической очистки старых образов и релизов нет.
- Python ML использует существующие незакреплённые зависимости из
  `ai/requirements-ml-api.txt`. Для полной воспроизводимости будущих пересборок
  потребуется отдельный lock-файл; откат использует уже собранные образы.
- Успешные локальные проверки не заменяют ввод CD в эксплуатацию на целевом
  сервере: реальные SSH, Telegram, DNS/TLS и восстановление production-БД
  здесь не проверялись.
