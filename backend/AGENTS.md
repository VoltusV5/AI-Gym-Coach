# Go backend

Действуют также [корневые правила](../AGENTS.md). Сохранять текущие имена пакетов, aliases импортов и архитектуру; не добавлять фреймворк ради локальной задачи.

## Слои и контракты
- `cmd/sport_app/main.go` собирает зависимости; `internal/core/` содержит общий HTTP, JWT, логирование и интерфейс пула; `internal/features/` — users, nutrition, mlclient/aichat.
- HTTP → service → repository: транспорт декодирует запрос и формирует ответ, сервис применяет бизнес-правила, репозиторий выполняет SQL. Интерфейсы зависимостей и моки держать по существующим примерам.
- Для защищённого маршрута применять `Protect(jwt)`, `userID` получать через `UserIDFromContext`. Гость также имеет JWT; ограничения зарегистрированных пользователей проверять по контракту операции. В SQL проверять владельца объекта, а не только его ID.
- Использовать `DecodeAndValidateRequest`, теги validator или `Validate() error`. Возвращать обёрнутые через `%w` ошибки `internal/core/errors`; статусы назначает `core/transport/http/responce`. Не возвращать клиенту секреты и внутренние реквизиты БД.
- Не менять действующие пути, JSON и пагинацию v1 без согласованного контракта. При изменении API синхронизировать `docs/api/` и `docs/postman/` в разрешённой области задачи.
- SQL параметризовать, соблюдать `OpTimeout()`, закрывать строки и проверять `rows.Err()`. Несколько связанных записей выполнять в транзакции; сохранять существующие проверки version/ErrConflict и deleted_at.
- Новые и изменённые функции документировать GoDoc: назначение, существенные аргументы/результат, ошибки и побочные эффекты. Сторонний и генерируемый код не переписывать.

## Запуск и проверки
Команды ниже выполнять из корня репозитория.

```sh
make -C backend verify
make -C backend lint-install  # установка закреплённой версии, нужен доступ к сети
make -C backend check         # verify + golangci-lint, как в CI
make -C backend test-cover    # полные логи и backend/coverage.out
cd backend && go test ./internal/features/users/repository/postgres -run TestGetListNotes -count=1
```

`verify` вызывает существующие цели `fmt-check`, `vet`, `test`, `build`, сохраняет полные логи во временный каталог и при первом сбое завершает работу с ненулевым кодом. Исходники не исправляет; сборка пишет `backend/out/sport_app`. Исправление форматирования — отдельная осознанная команда `make -C backend fmt`.
Go 1.25.5 соответствует `go.mod`, CI и default в Dockerfile. Для точного повторения локально можно задать `GOTOOLCHAIN=go1.25.5`; первая загрузка toolchain требует сети. Не обновлять Go/зависимости вне задачи.

Локальный запуск: создать `backend/.env` по `backend/.env.example`, заполнить `JWT_*`, `POSTGRES_*`, `ML_*`, `LOGGER_*`, `HTTP_*`, затем выполнить `make -C backend sportapp-run`. Для запущенного из host API БД доступна после `make -C backend env-up env-port-forward` на `POSTGRES_HOST=127.0.0.1`, `POSTGRES_PORT=5433`; `HTTP_ADDR=:5050`. Миграции применяет человек к проверенной целевой БД. ML должен быть доступен по настроенным URL для сценариев генерации и чата.

## Проверки без рабочей БД
Обычные `go test ./...` и `verify` не должны требовать запущенную БД или внешний AI: использовать моки и `httptest`. Для исправления ошибки сначала воспроизвести её целевым тестом. Интеграционный прогон допускается только с явно выбранной отдельной одноразовой БД и фикстурами; никогда не брать рабочие реквизиты по умолчанию. Не запускать `env-cleanup` и не удалять `out/pgdata`.
