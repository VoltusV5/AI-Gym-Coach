# Профиль пользователя v2

Реализация V2-21 использует существующие HTTP → service → repository и общую с v1 таблицу `sportapp.profile`. Применяется после справочников V2-20. Контракт Go backend: [profile-v2.openapi.json](profile-v2.openapi.json); исходный план API находится в `docs/api/semester.json`. Файлы frontend, ML и общего просмотрщика документации этой задачей не изменяются.

## API

`GET /api/v2/me/profile` и `PATCH /api/v2/me/profile` требуют Bearer JWT. Гостевая анкета доступна, чтобы сохранить onboarding. `user_id` берётся только из JWT; передать его в PATCH нельзя.

```json
{
  "version": 1,
  "weight_kg": 75.25,
  "level": "intermediate",
  "training_days": [1, 3, 7],
  "equipment_ids": ["dumbbell", "bench"],
  "session_duration_min": 45,
  "excluded_exercise_ids": [1]
}
```

Ответ — сохранённая анкета с увеличенной `version`. Дни ISO 1–7 возвращаются по возрастанию; оборудование и исключения — по ID. Пустые массивы очищают списки, пропущенные поля сохраняются. Незаполненные скалярные поля в GET возвращаются как `null`; PATCH не принимает `null`, неизвестные поля, дубли элементов и дополнительные JSON-значения после объекта.

`level`: `beginner`, `intermediate`, `advanced`. Остальные существующие строковые поля сохраняют значения анкеты v1. При PATCH возраст, рост и длительность должны быть положительными INTEGER; вес — положительным конечным числом, представимым в целочисленной проекции v1. Старые нули, отрицательные целые и пустые строки при чтении не исправляются автоматически. Оборудование должно существовать, новые исключения должны ссылаться на активные упражнения. `injuries_notes` остаётся boolean; диагнозы и исключения из него не выводятся.

Неверный ввод — 400, неверный/отсутствующий JWT — 401, отсутствующая анкета — 404, устаревшая версия — 409. Ошибки v2 имеют `error.code`, `error.message`, `request_id` и не включают SQL, секреты или содержимое анкеты.

## Хранение и совместимость

Миграция `000008_profile_v2.up.sql` переводит `profile.weight_kg` из INTEGER в NUMERIC, добавляет `session_duration_min` и таблицу `profile_excluded_exercises`. Для оборудования переиспользуется `profile_equipment` из миграции 000007. ID и существующие записи не пересоздаются.

GET v1 сохраняет целочисленный JSON веса: `weight_kg::integer` округляет по правилам PostgreSQL, например 75.25 → 75, 75.75 → 76. Исходный дробный вес остаётся в NUMERIC и доступен через v2. Старые целые значения читаются без изменений. Дни и уровень v2 при сохранении преобразуются в коды v1 (`mon`…`sun`, `Новичок`/`Любитель`/`Продвинутый`); существующие русские сокращения дней также читаются. Неизвестные прежние значения уровня не перезаписываются автоматически и имеют `level: null` в v2.

PATCH блокирует строку своей анкеты, проверяет `version` и ID, обновляет поля и списки в одной транзакции и возвращает результат до освобождения блокировки. Из двух запросов с одной версией записывается только один. Ошибки проверки и конфликт не оставляют частичных изменений.

Откат 000008 удаляет новые длительности и исключения, поэтому перед реальным откатом их нужно экспортировать. При наличии дробных весов down завершается ошибкой до изменений: нельзя молча округлять данные. Оператор должен сохранить исходные значения и явно решить, как подготовить данные к INTEGER. Данные оборудования, анкеты и v1-таблицы сохраняются.

## Проверки

Из корня репозитория:

```sh
(cd backend && go test ./internal/features/profile/... -count=1)
make -C backend check
```

Обычные тесты используют моки и `httptest`, интеграционный тест пропускается без явного `SPORTIK_PROFILE_TEST_DB`. Интеграционный тест принимает только новую БД `sportik_profile_test_*` на выделенном `127.0.0.1:55443` с ролью `sportik_test`. Существующая схема считается ошибкой и никогда не очищается. Рабочая `.env` не используется.

Для интеграционного прогона подготовить отдельный одноразовый PostgreSQL 18. Пример при наличии PostgreSQL CLI в PATH:

```sh
profile_test_root=$(mktemp -d "${TMPDIR:-/tmp}/sportik-profile-test.XXXXXX")
profile_test_db="sportik_profile_test_$(date +%s)"
initdb -D "$profile_test_root/data" -U sportik_test -A trust -E UTF8 --no-locale
pg_ctl -D "$profile_test_root/data" -l "$profile_test_root/server.log" \
  -o "-h 127.0.0.1 -p 55443 -k $profile_test_root" start
createdb -h 127.0.0.1 -p 55443 -U sportik_test "$profile_test_db"
(cd backend && SPORTIK_PROFILE_TEST_DB="$profile_test_db" \
  go test ./internal/features/profile/repository/postgres -run TestProfileIntegration -count=1 -v)
pg_ctl -D "$profile_test_root/data" stop -m fast
```

Каждый повторный прогон требует новую пустую БД. Тест проверяет чистую и заполненную v1-схему, up/down/up, защиту отката от потери дробных значений, дробный вес, права, ошибки ID, конфликт версий, два конкурентных обновления и чтение через новое подключение. Рабочую БД, `env-cleanup` и очистку томов для этого не использовать.
