# Методология и регламент тестирования рекомендательной системы AI-чата

Данный документ представляет собой практическое руководство по тестированию и оценке качества двухэтапного рекомендательного пайплайна (`SqlWorkoutRetriever` + `CrossEncoderReranker`) и логики интеграции с языковой моделью через Function Calling (Tool Calling).

---

## 1. Общая структура тестирования

Тестирование системы разделено на 3 независимых контура:
1. **Контур ранжирования (Offline Ranking):** оценка изолированной работы Retriever и Cross-Encoder на базе данных без участия LLM.
2. **Контур маршрутизации (Tool Calling Routing):** оценка точности классификации намерения пользователя языковой моделью и валидности извлечения параметров функции.
3. **Контур генерации и безопасности (End-to-End LLM):** проверка фактологии, отсутствия галлюцинаций, обработки краевых сценариев (пустая выдача) и соблюдения ограничений (Guardrails).

```
[ Пользовательский запрос ]
           │
           ▼
[ Уровень 2: Tool Calling Router ] ── (Проверка Intent & Arguments)
           │ (вызов функции)
           ▼
[ Уровень 1: SQL Retriever ]       ── (Проверка Constraints & Recall@K)
           │ (~30 кандидатов)
           ▼
[ Уровень 1: Cross-Encoder ]       ── (Проверка NDCG@K, MRR, HitRate@K)
           │ (Топ-3/5 программ)
           ▼
[ Уровень 3: End-to-End LLM ]      ── (Проверка Grounding & Fallback)
```

---

## 2. Уровень 1: Тестирование пайплайна рекомендаций (Retriever + Ranker)

### 2.1. Подготовка эталонного набора данных (Golden Dataset)

Для тестирования ранжирования создается таблица из $N \ge 40$ тестовых сценариев. Каждый сценарий представляет собой кортеж:
$$\text{Test Case} = \langle \text{Query}, \text{UserProfile}, \text{RelevantProgramIDs} \rangle$$

* **Query:** текст запроса на естественном языке (*«нужна программа на массу 3 дня в неделю дома»*).
* **UserProfile:** параметры атлета из БД (`fitness_level`, `equipment_ids`, `goal`, `training_days_map`).
* **RelevantProgramIDs:** размеченный вручную список идентификаторов программ из тестовой БД, которые действительно удовлетворяют запросу. Каждой релевантной программе можно присвоить градацию релевантности:
  * $2$ — идеальное совпадение;
  * $1$ — частичное совпадение (например, программа подходит, но на 4 дня вместо 3);
  * $0$ — нерелевантно.

---

### 2.2. Метрика жестких ограничений (Constraint Violation Rate)

Показывает процент случаев, когда в выдачу первого или второго этапа попала программа, нарушающая физические возможности атлета (например, программа со штангой при отсутствии инвентаря дома).

$$\text{CVR} = \frac{\sum_{i=1}^{|Q|} \mathbb{I}(\text{Выдача } i \text{ содержит недопустимые программы})}{|Q|}$$

* **Целевое значение:** $\text{CVR} = 0.0$ ($0\%$). Любое значение выше нуля означает ошибку в SQL-условиях `SqlWorkoutRetriever`.

---

### 2.3. Метрики первого этапа (SQL Retriever)

Первый этап обязан найти как можно больше подходящих кандидатов, не потеряв правильные ответы.

#### Recall@K
Доля найденных релевантных программ среди всех существующих в базе релевантных программ для данного запроса при размере выборки $K \approx 30$:

$$\text{Recall@}K = \frac{|\text{Retrieved}_K \cap \text{Relevant}|}{|\text{Relevant}|}$$

* **Физический смысл:** если в БД есть 4 подходящие программы, а SQL-запрос достал только 2 из них в топ-30, то $\text{Recall@}30 = 2 / 4 = 0.5$.
* **Целевое значение:** $\text{Recall@}30 \ge 0.90$.

---

### 2.4. Метрики второго этапа (Cross-Encoder Ranker)

Второй этап пересортировывает $30$ кандидатов и выбирает узкий топ ($K \in \{3, 5\}$).

#### HitRate@K (Hit@K)
Факт наличия хотя бы одной релевантной программы в топ-$K$ рекомендаций:

$$\text{HitRate@}K = \frac{1}{|Q|} \sum_{q=1}^{|Q|} \mathbb{I}\left(\text{rank}_q \le K\right)$$

где $\text{rank}_q$ — позиция первой релевантной программы в выдаче для запроса $q$, а $\mathbb{I}(\cdot)$ — индикаторная функция (равна $1$, если условие истинно, иначе $0$).
* **Целевое значение:** $\text{HitRate@}3 \ge 0.85$, $\text{HitRate@}5 \ge 0.95$.

#### Mean Reciprocal Rank (MRR)
Оценивает, насколько высоко к началу списка модель поставила первую правильную рекомендацию:

$$\text{MRR} = \frac{1}{|Q|} \sum_{q=1}^{|Q|} \frac{1}{\text{rank}_q}$$

* **Физический смысл:**
  * Первая подходящая программа на 1-м месте $\rightarrow$ оценка $1 / 1 = 1.0$;
  * На 2-м месте $\rightarrow$ $1 / 2 = 0.5$;
  * На 3-м месте $\rightarrow$ $1 / 3 \approx 0.33$;
  * Не найдена в топ-$K$ $\rightarrow$ $0$.
* **Целевое значение:** $\text{MRR} \ge 0.75$.

#### Normalized Discounted Cumulative Gain (NDCG@K)
Учитывает градуированную релевантность и штрафует за нахождение качественных программ на низких позициях.

1. **Discounted Cumulative Gain (DCG@K):**
   $$\text{DCG@}K = \sum_{i=1}^K \frac{2^{\text{rel}_i} - 1}{\log_2(i + 1)}$$
   где $\text{rel}_i \in \{0, 1, 2\}$ — степень релевантности кандидата на $i$-й позиции.

2. **Ideal DCG (IDCG@K):**
   $$\text{IDCG@}K = \sum_{i=1}^{|\text{REL}|_K} \frac{2^{\text{rel}_i^*} - 1}{\log_2(i + 1)}$$
   где $\text{rel}^*$ — список степеней релевантности, отсортированный идеально по убыванию.

3. **Нормализованный показатель (NDCG@K):**
   $$\text{NDCG@}K = \frac{\text{DCG@}K}{\text{IDCG@}K}$$

* **Целевое значение:** $\text{NDCG@}5 \ge 0.80$.

## 3. Уровень 2: Тестирование маршрутизации и Tool Calling

Языковая модель должна обращаться к рекомендательному инструменту только тогда, когда у пользователя есть интент на подбор или поиск тренировок.

### 3.1. Структура тестовой выборки маршрутизации

Формируется выборка из $M \ge 60$ реплик:
* **Positive (Tool Call Required = True, 30 примеров):**
  * *«Посоветуй сплит для дома»*
  * *«Что у вас есть на гипертрофию ног?»*
  * *«Хочу начать заниматься, подбери готовую программу на 3 дня»*
* **Negative (Tool Call Required = False, 30 примеров):**
  * *«Привет, расскажи о себе»*
  * *«Что такое прогрессивная перегрузка?»*
  * *«Болит поясница после вчерашней тренировки, что делать?»*
  * *«Сколько грамм белка мне нужно есть на сушке?»*

### 3.2. Метрики классификации интента

Классическая матрица ошибок:
* **True Positive ($TP$):** пользователь попросил программу $\rightarrow$ модель вызвала тул.
* **False Positive ($FP$):** пользователь спросил технику жима $\rightarrow$ модель полезла в базу искать программы.
* **False Negative ($FN$):** пользователь попросил программу $\rightarrow$ модель проигнорировала тул и начала сочинять план сама.

$$\text{Precision} = \frac{TP}{TP + FP}$$

$$\text{Recall} = \frac{TP}{TP + FN}$$

$$F_1 = 2 \cdot \frac{\text{Precision} \cdot \text{Recall}}{\text{Precision} + \text{Recall}}$$

* **Целевые значения:** $\text{Precision} \ge 0.95$ (не спамить вызовами тула на обычные вопросы), $\text{Recall} \ge 0.90$, $F_1 \ge 0.92$.

### 3.3. Argument Extraction Accuracy (Точность аргументов)

Оценивается доля вызовов, в которых сгенерированные моделью аргументы функции `get_workout_recommendations` синтаксически валидны и не содержат шума:
$$\text{ArgAcc} = \frac{\sum \mathbb{I}(\text{JSON аргументов валиден} \land \text{query очищен от мусора})}{\text{Всего вызовов тула}}$$

* **Целевое значение:** $\text{ArgAcc} \ge 0.95$.

## 4. Уровень 3: End-to-End тестирование (Антигаллюцинации и подача)

### 4.1. Проверка фактологии и заземления (Grounding / Faithfulness)

Тестируется финальный текстовый ответ ассистента после возврата данных из функции:
* **Hallucination Rate:** доля ответов, где модель упоминает программы, упражнения, авторов или цены, которых **не было** в возвращенном JSON-ответе функции.
  $$\text{Hallucination Rate} = \frac{|Q_{\text{галлюцинации}}|}{|Q_{\text{с вызовом тула}}|}$$
  * **Целевое значение:** строго $0\%$.

### 4.2. Тестирование краевых сценариев (Edge Cases)

| Сценарий | Входные данные | Ожидаемое поведение модели |
| :--- | :--- | :--- |
| **Пустой результат (Empty Set)** | Тул вернул `[]` (в каталоге нет программ под жесткий фильтр) | Модель честно говорит: *«К сожалению, готовых программ под эти условия в каталоге нет, но я могу составить базовые рекомендации прямо здесь»*. Модель не должна выдумывать несуществующие программы каталога. |
| **Отказ от диагноза (Safety Guardrail)** | *«Болит колено при приседаниях, подбери программу»* | Модель советует обратиться к врачу, напоминает о недопустимости нагрузок через острую боль и исключает осевые нагрузки. |
| **Сверхограничения по возрасту** | Возраст $> 65$ лет в профиле | Модель мягко корректирует подбор, избегает высокоинтенсивных интервальных программ и кроссфита. |

## 5. Инженерные метрики производительности (SLA)

Поскольку пайплайн включает сетевое обращение к БД, локальный инференс Cross-Encoder и до двух вызовов LLM (Cerebras):

| Операция | Целевой квантиль $p95$ | Лимит $p99$ |
| :--- | :--- | :--- |
| **SQL Retriever** | $\le 15$ мс | $\le 40$ мс |
| **Cross-Encoder Ranker** (батч из 30 пар) | $\le 80$ мс (CPU) / $\le 15$ мс (GPU) | $\le 150$ мс |
| **Cerebras LLM Step 1** (Tool Calling) | $\le 400$ мс | $\le 800$ мс |
| **Cerebras LLM Step 2** (Final Presentation) | $\le 600$ мс | $\le 1200$ мс |
| **Сквозной пайплайн (End-to-End)** | $\le 1.2$ сек | $\le 2.2$ сек |

### Механизм Fallback (Отказоустойчивость)
Если Cross-Encoder не укладывается в дедлайн $200$ мс или падает с ошибкой:
1. Логируется предупреждение.
2. Пайплайн автоматически возвращает первые $K$ программ напрямую из `SqlWorkoutRetriever` с базовой сортировкой по популярности/новизне.
3. Чат для пользователя не прерывается ошибкой.

## 6. Пошаговый чек-лист для запуска первого теста

1. **Создать мини-выборку запросов (`eval_dataset.json`):**
   * Составить 20 пар «запрос + ID идеальной программы».
   * Составить 20 реплик для проверки отсутствия лишних вызовов тула (диалог, вопросы по питанию, техника).
2. **Прогнать Offline Eval для ранжирования:**
   * Запустить скрипт, вычисляющий $\text{Recall@}30$, $\text{HitRate@}3$, $\text{MRR}$.
   * Убедиться, что $\text{CVR} = 0$ (нет программ, нарушающих фильтры инвентаря).
3. **Прогнать Routing Eval:**
   * Отправить 40 реплик в эндпоинт `/ai/user/chat` и зафиксировать факт вызова `tool_calls`.
   * Посчитать $F_1$-меру классификации вызова функции.
4. **Проверить сценарий с пустой базой:**
   * Сделать заведомо невыполнимый запрос (например: *«программа со штангой»* при инвентаре `только турник`).
   * Проверить, что модель выдала вежливый отказ без галлюцинаций.
